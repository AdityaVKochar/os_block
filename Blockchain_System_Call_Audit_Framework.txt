BLOCKCHAIN-BASED SYSTEM CALL AUDIT FRAMEWORK
Immutable Audit Logs Using Lightweight Blockchain Principles

PROJECT BRIEF (humanized, presentation-ready)

1. INTRODUCTION

Every operating system is constantly making small but important decisions: which process may open a file, start another program, create a network connection, or change permissions. These actions cross the kernel boundary through system calls. When an attacker compromises a machine, or when a privileged user misuses access, the sequence of system calls is often the most useful forensic evidence.

The problem is that ordinary log files are usually stored on the same machine that creates them. A person who has administrator or root access can alter, delete, or replace those files. A log that cannot be trusted cannot reliably support incident response, compliance, or accountability.

This project proposes a Blockchain-Based System Call Audit Framework (B-SCAF). It does not attempt to run a costly public cryptocurrency blockchain inside an operating system. Instead, it borrows the useful ideas: cryptographic hashing, chained records, Merkle-tree batching, digital signatures, distributed witnessing, and independently verifiable checkpoints. Raw system-call events remain off-chain in protected storage; only compact integrity commitments and metadata are chained and periodically anchored. This makes the proposal realistic for a lab prototype and suitable for high-volume audit data.

The central promise is simple: the framework should make a changed, removed, reordered, or inserted audit event detectable, while adding only modest performance overhead.


2. IDEOLOGY / DESIGN PHILOSOPHY

The project is guided by five practical beliefs:

• Evidence should outlive the machine that produced it. A compromised endpoint must not be the only keeper of its own history.
• Immutability should be verifiable, not merely claimed. An auditor should be able to recompute hashes and see exactly where a mismatch occurs.
• “Blockchain-based” should not mean “store everything on-chain.” System-call streams are large and may contain sensitive information; a hash-first, off-chain design is more responsible.
• Security should be measurable. The framework must report latency, throughput, storage growth, verification time, and CPU impact—not only security features.
• Audit tools must remain usable. Security staff need searchable, readable events and a clear integrity verdict, rather than a cryptography-only prototype.


3. PROBLEM STATEMENT

Traditional host audit logs can be modified or destroyed by a privileged attacker, a malicious administrator, malware with elevated permissions, or an accidental configuration change. Centralizing logs improves availability but can still leave one trusted party with the power to rewrite evidence. Conversely, writing every system-call event to a conventional blockchain is impractical because of transaction latency, storage cost, privacy exposure, and consensus overhead.

How can a Linux host record security-relevant system calls in a way that is tamper-evident, independently verifiable, privacy-aware, and lightweight enough for normal system operation?


4. IDENTIFIED RESEARCH GAP

Recent blockchain logging work strongly establishes the value of immutable audit trails, but much of it focuses on cloud events, healthcare access, IoT data, or enterprise application logs. System-call research, meanwhile, often focuses on detecting intrusions from sequences rather than preserving those sequences as legally and operationally trustworthy evidence.

The gap is the integration of both concerns in one practical host-level design:

1. Fine-grained collection: capture selected Linux system calls with process context.
2. Tamper evidence: chain canonical event batches and protect each batch with a Merkle root.
3. Independent audit: allow another machine or verifier to validate stored events without trusting the source host.
4. Lightweight operation: avoid per-event blockchain transactions and avoid storing sensitive raw event content on the ledger.
5. Useful forensics: retain searchable event records, proof paths, checkpoint references, and a human-readable verification report.


5. NOVELTY OF THE PROPOSED PROJECT

The novelty is not the claim that blockchain alone makes logs secure. The contribution is a focused, lightweight combination for operating-system audit evidence:

• Kernel-to-proof pipeline: security-relevant system calls are normalized into a deterministic event format before hashing. This connects OS telemetry with a verifiable evidence structure.
• Dual-level integrity: each event is hash-linked locally, while a Merkle root commits a whole time window. This supports both fast batch verification and proof of one specific event.
• Permissioned witness model: a small set of departmental or lab verifier nodes signs/checkpoints batch roots. This avoids proof-of-work cost while reducing dependence on one log administrator.
• Privacy-preserving ledger entries: the chain carries hashes, timestamps, batch identifiers, and signatures—not command-line arguments or raw file paths unless explicitly authorized.
• Failure-aware audit result: verification reports distinguish missing batches, altered records, broken chain links, invalid signatures, and unavailable witnesses. That makes the output useful during an investigation.

Novelty claim, stated carefully: B-SCAF is a proposed integration and prototype contribution. It should be presented as a lightweight adaptation of established cryptographic and blockchain principles for host system-call auditing—not as a claim to invent hashing, Merkle trees, or secure logging.


6. PROJECT OBJECTIVES

Objective 1 – Capture meaningful host activity
Develop a Linux collector using eBPF/auditd-compatible mechanisms to capture a configurable set of security-relevant system calls (for example execve, openat, unlinkat, connect, chmod, setuid and ptrace) with PID, parent PID, UID, timestamp, return status, and selected arguments.

Objective 2 – Build an immutable, lightweight evidence chain
Convert normalized events into fixed-format records; hash-link them; group them into short batches; compute a Merkle root; and place the root plus a digital signature in a permissioned checkpoint ledger.

Objective 3 – Provide independent verification
Create a verifier that recomputes event hashes, checks chain continuity, rebuilds Merkle roots, validates signatures, and produces a clear pass/fail/partial-evidence audit report.

Objective 4 – Evaluate real-world practicality
Measure event-ingestion throughput, average capture-to-commit delay, CPU and memory overhead, storage growth, and verification time under benign workloads and controlled tampering tests.


7. METHODOLOGY / TECHNIQUE

Phase 1: Requirements and threat model
Define the protected assets (event integrity, order, origin, availability and confidentiality) and attacker abilities. The prototype should assume an attacker can edit local log files after gaining high privileges. It should not claim to prevent a fully compromised kernel from fabricating events before collection; that limitation must be stated honestly.

Phase 2: System-call acquisition
Use Linux eBPF tracepoints/kprobes or auditd rules to collect the chosen calls. A user-space agent adds process metadata, applies field minimization/redaction, and serializes events in canonical JSON or a fixed binary schema. Canonicalization is essential: two equivalent events must hash to the same byte sequence.

Phase 3: Local evidence construction
For event i, calculate:

    event_hash_i = SHA-256(canonical_event_i || event_hash_(i-1))

For every N events or T seconds, build a Merkle tree over event hashes. Store raw events and proof data in an append-only local database/object store. The batch root becomes the compact commitment for that interval.

Phase 4: Lightweight blockchain checkpointing
Create a block containing batch ID, previous block hash, Merkle root, source-node ID, timestamp, policy version, and signer signature. Replicate the block to 3–5 known verifier nodes using a permissioned protocol or a simple signed, quorum-acknowledged append-only ledger. A Hyperledger Fabric test network is optional; a custom permissioned prototype is acceptable if its assumptions are documented.

Phase 5: Verification and attack tests
Test at least these cases: modify one raw event, delete an event, insert an event, reorder events, modify a stored Merkle root, replay an old batch, and take one witness node offline. The verifier should identify the first invalid item or clearly report the missing evidence.

Phase 6: Evaluation
Compare: (a) ordinary local logging, (b) hash-chain-only logging, and (c) B-SCAF. Run a repeatable workload such as file operations, process creation and network connections. Report median and p95 latency, events/second, CPU percentage, memory, storage per event, and verification time for one event and for one full batch.

9. EXPECTED OUTCOMES

• A working prototype that collects selected system calls and produces verifiable batches.
• A tamper-evidence demonstration: any tested modification to a committed event is detected.
• A small dashboard or command-line report that gives auditors an understandable integrity verdict.
• A measured overhead profile and a documented limit of the approach.
• A reproducible test dataset, threat model, and evaluation script for future extension.


10. DETAILED LITERATURE REVIEW

The literature falls into three connected streams.

A. Immutable and blockchain-backed logging
Ali et al. (2021) proposed BCALS for secure cloud log management and explicitly addressed administrator-level modification risks. Ahmad et al. (2022) showed the promise and cost trade-off of blockchain-driven audit trails. Regueiro et al. (2021), López-Pimentel et al. (2021), Aslan and Şen (2021), and Pawar et al. (2021) demonstrate audit-trail and log-registration designs. Li et al. (2024) directly addresses the practical tension between protected log storage and efficient querying. Austin and Di Troia (2023) and Guardiola-Múzquiz and Soriano-Salvador (2023) provide useful tamper-resistant logging perspectives, including a non-blockchain alternative based on ratcheting and protected storage.

These works justify integrity commitments, but they also reveal why raw logs should not be copied blindly to a chain: performance, searchability, and privacy matter.

B. Domain-specific audit trails and provenance
Pattengale and Hudson (2020), Ma et al. (2020), and Adlam and Haskins (2020) apply permissioned blockchain ideas to sensitive healthcare/genomics access logs. Zhao et al. (2023) and Zhao et al. (2020) show secure logging for sensing and IoT events. These systems reinforce a design principle useful here: preserve detailed data off-chain and use a ledger for integrity proof and trusted ordering.

C. System-call sequence analysis and host intrusion detection
Byrnes et al. (2020), Zhang et al. (2021), Chaudhari et al. (2023), Wan et al. (2023), and Vyšniūnas et al. (2024) demonstrate that system-call sequences are valuable host-security signals. Zipperle et al. (2022) surveys provenance-based intrusion detection. This body of work is strong on detecting suspicious behavior, but it does not by itself guarantee that the underlying sequence has not been changed after collection. B-SCAF uses system-call records as durable evidence first; detection models can be added later without replacing the integrity layer.

D. Design implications for this project
The reviewed work supports batching, off-chain storage, permissioned participation, integrity proofs, and independent auditing. The proposed framework combines these lessons around the overlooked host-level evidence path. It deliberately avoids claiming that blockchain prevents all attacks: it detects changes to committed evidence, while trustworthy collection still depends on the integrity of the host and collector at capture time.

12. PRESENTATION / VIVA TALKING POINTS

Opening line: “Logs are useful only when we can trust them. This project makes system-call evidence verifiable even after it leaves the host.”

Why not a normal database? A database can control access and keep backups, but a privileged administrator can still alter records. B-SCAF exposes such alteration through hashes, signed checkpoints, and external witnesses.

Why not put every event on blockchain? It would be slow, expensive, hard to search, and may expose private data. We store detailed events off-chain and commit only compact cryptographic proofs.

What does the project guarantee? It makes post-commit modification, deletion, insertion, and reordering detectable, provided the checkpoint ledger and at least the required witness quorum remain trustworthy.

What does it not guarantee? It cannot prove that a fully compromised kernel did not lie before collection. This is a capture-trust limitation; future work can use TPM-backed attestation, remote collection, or hardware security modules.

Adherence-to-time plan (12 weeks): Weeks 1–2 literature/threat model; 3–4 collector and schema; 5–6 hash chain and Merkle batches; 7–8 signed witness ledger; 9 verifier/UI; 10 attack testing; 11 performance evaluation; 12 report, demo and presentation.
